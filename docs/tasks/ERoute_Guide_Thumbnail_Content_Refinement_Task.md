# ERoute 가이드 v1.1 — 썸네일 목록·읽기용 상세·항목별 공개 조건 정리

작성일: 2026-09-16  
용도: 현재 ERoute 저장소에서 Codex가 수행할 후속 작업 명세  
상태: 구현 지시안. 앱 수정·썸네일 제작·의료 원고 승인·공개 배포가 완료됐다는 뜻이 아니다.

## 1. 목표와 현재 근거

기존 응급 가이드 모듈을 재사용해, 일반 앱에서 주제를 그림으로 구분하는 썸네일 목록과 읽기용 상세를 개선한다. 동시에 7개 원고의 공개를 막고 있는 질문을 항목별로 검토한다. 새 Preview 앱이나 별도 가이드 시스템을 만들지 않는다.

사용자가 제공한 2026-09-15 보고서와 콘텐츠 매트릭스에 따른 출발점:

- 일반 랜딩의 두 메뉴는 이미 목록·상세에 연결되어 있다. 일반 상세는 상태·출처만 보여준다.
- 제1유형 자료에 근거한 실제 부분 원고 7건이 있으며, 매트릭스에는 해당 텍스트의 권리가 확인된 것으로 기록되어 있다.
- 공개 가능한 본문은 0건이다. 의료 검토와 공개 승인은 PENDING, 실제 검토자·검토일은 null이다.
- 일반 앱 → 앱 정보 → 개발 검수 경로에서 검토용 원고를 볼 수 있다. 일반/검수 화면은 공통 위젯을 사용한다.
- 번들 열람, 오프라인 첫 실행, 외부 링크 실패 후 복귀와 production 원고 제외 검사가 구현되어 있다.
- Flutter 157건 통과가 기록되어 있다. TalkBack 한국어 음성·연속 탐색과 실물 기기/iOS 검수는 미완료다.

위 내용은 보고서상 상태이며, 이번 실행자가 현 저장소와 실제 산출물을 다시 확인한다. 첨부 매트릭스에는 개별 원고 전체가 없으므로 요약만으로 본문을 승인하지 않는다.

읽을 자료:

- `docs/qa/emergency-guides-v1-2026-09-15/README.md`
- `docs/content/emergency-guides/content-matrix.md`
- `docs/content/emergency-guides/source-register.md`
- `docs/content/emergency-guides/decisions.md`
- `docs/content/emergency-guides/drafts/`의 7개 실제 원고
- `docs/tasks/ERoute_Emergency_Guides_v1_Task.md`
- 현재 `AGENTS.md`, `DESIGN.md`, `UX-CONTRACT.md`, 실행 스크립트와 가이드 모듈

이번 수정 사항이 기존 명세와 충돌하면 차이를 먼저 기록한다. 최신 회원 인증을 과거 PASS 기반 설정으로 되돌리지 않는다.

## 2. 이번 범위와 종료선

세 작업을 함께 진행한다.

1. 동일한 책 아이콘 목록을 주제별 썸네일 카드로 바꾼다.
2. 읽기용 안내와 내부 검토 정보를 분리한다. 원문 링크는 보조로 유지한다.
3. 원고별 미해결 질문의 필요성·근거·해결 방법을 정리하고, 근거로 해결 가능한 부분은 실제 원고에 반영한다.

썸네일 승인, 내용의 근거 확인, 의료 검토, 이용권한 확인, 공개 배포 승인은 서로 다르다. 썸네일과 UI를 승인했다고 의료 원고의 상태를 변경하지 않는다.

원고가 모두 미승인인 경우에도 썸네일과 상태 화면은 일반 앱에 적용할 수 있다. 그러나 해당 카드를 완성된 처치 안내로 오해시키지 않는다. 실제 공개 본문 수를 따로 보고한다.

## 3. 썸네일형 목록의 디자인 계약

### 3.1 전체 구조

- 기존 두 랜딩 버튼과 메뉴 구분을 유지한다.
- 상단 제목은 한 번만 크게 표시한다. AppBar 제목과 같은 대형 제목을 바로 반복하지 않는다.
- 119 진입은 상단에 쉽게 찾을 수 있는 기존 버튼으로 유지한다. 안내 열람·로그인·GPS 성공을 요구하지 않는다.
- 목록은 기본 한 열이며, 카드 왼쪽에 주제 그림, 오른쪽에 제목·짧은 설명·대상·이용 상태를 둔다.
- 카드 탭의 기본 목적지는 내부 상세다. 전체 카드를 외부 웹페이지로 연결하지 않는다.
- 영상 기능이 아니므로 재생 아이콘, 영상 길이, 조회수, 가상 별점은 넣지 않는다.
- 이미지가 글자를 대신하지 않는다. 제목·설명·대상·준비 상태는 Flutter 텍스트로 렌더링한다.

레이아웃 제안값은 기존 토큰과 실제 화면에 맞춰 검수한다.

- 썸네일은 대략 104~120dp 너비의 16:10 비율을 시작점으로 한다. 작은 책 아이콘을 배경색만 바꾼 결과를 썸네일 완성으로 보고하지 않는다.
- 좁은 너비나 큰 글씨에서는 그림 위/본문 아래의 카드로 재배치할 수 있다. 내용을 맞추려고 글자를 축소하거나 제목·대상·상태를 잘라내지 않는다.
- 기존 흰색 카드, 약한 경계와 그림자, 파스텔 강조색, 남색 제목, Noto Sans KR를 유지한다.
- 새 폰트·상태관리·디자인 시스템이나 일반 앱의 전면 테마 변경은 도입하지 않는다.
- 카드 전체가 하나의 탐색 동작이 되게 하되, 이미지와 화살표가 별도 중복 접근성 초점을 만들지 않게 한다.

### 3.2 주제별 썸네일 제작 범위

아래는 의료 절차를 지시하는 그림이 아니라 주제를 식별하는 자체 일러스트의 디자인 방향이다.

| 가이드 ID | 주제 | 그림 방향 | 추가하지 않을 것 |
|---|---|---|---|
| report-119 | 119에 알려줄 내용 | 휴대폰·말풍선·메모 | 개인정보가 적힌 실제 화면, 전송 완료 표시 |
| explain-location | 주소를 모를 때 | 위치 핀·단순한 건물 | 실제 지역 지도, 사용자 좌표, GPS 성공 배지 |
| before-ambulance | 구급차 도착 전 | 일반 구급차와 도착을 나타내는 배경 | 현장 처치 자세, 출동 보장 문구 |
| adult-cpr | 성인 심폐소생술 | 심장과 도움을 상징하는 비절차적 그림 | 가슴압박 위치·깊이·속도·자세의 미검수 표현 |
| adult-aed | 성인 자동심장충격기 | 제조사 표시 없는 일반 AED 기기 | 패드 부착 위치·버튼 조작·전기 충격 과정 |
| external-bleeding | 외부 출혈·상처 | 거즈·붕대 등 관련 물품 | 출혈 사진, 지혈대 위치·압박 자세 |
| thermal-burn | 열에 의한 화상 | 열을 상징하는 추상 모티프 | 손상 피부, 냉각 수치·시간·처치 순서 |

공통 제작 조건:

- 같은 그림 스타일과 색감으로 7개를 제작한다. 공포감·유혈·광고성 표현은 피한다.
- 이미지에는 제목·숫자·119·안내 문장을 굽지 않는다. 필요한 문자는 앱에서 표시한다.
- 기관 로고·인증 마크·붉은 십자 표장을 장식으로 넣지 않는다. ERoute를 공식 기관 앱처럼 표현하지 않는다.
- 기존 공식 이미지나 영상 썸네일을 무단 캡처·재가공하거나, 웹페이지에서 실시간 수집하지 않는다.
- 이미지 생성 도구를 쓰는 경우 비절차적 주제 일러스트에 한정한다. 생성 도구 사용을 의료 검토·권리 보장과 동일하게 보고하지 않는다.
- 도구로 만들지 못한 경우 필요한 자산을 명시하고, 기본 아이콘이나 빈 박스를 완성 썸네일로 보고하지 않는다.
- 새 의료 도해를 꼭 추가해야 한다면 이번 장식 작업에 끼워 넣지 않고 별도 정확성·권리 검토 대상으로 남긴다.

자산은 개별 파일로 저장한다. 원본은 예를 들어 768×480px, 목록용 파생본은 384×240px의 PNG/WebP를 시작점으로 삼되 실제 선명도·파일 크기로 조정한다. 래스터를 벡터 원본이라고 기록하지 않는다. 발표용 비교표에서 잘라낸 작은 그림을 원본으로 삼지 않는다.

## 4. 현재 공개 본문 0건을 반영하는 화면

현재 상태를 정직하게 유지하면서, 과도한 개발 현황 설명이 주제 목록을 밀어내지 않도록 한다.

| 상태 | 목록 | 카드 탭 후 |
|---|---|---|
| 공개 승인 본문 존재 | 주제 그림·제목·대상, 실제로 읽을 수 있음을 표시 | 내부 번들 본문 |
| 본문 공개 준비 중 | 같은 주제 그림 + 눈에 띄는 `본문 준비 중` 텍스트 | 간결한 준비 상태·대상·출처 화면 |
| 자산/본문 손상 | 읽기 실패를 명확히 구분 | 재시도·목록 복귀, 다른 안내와 119 유지 |

- 현재 공개 가능한 항목이 0개라면 목록 상단에 `가이드 본문을 준비하고 있습니다. 공식 자료는 출처에서 확인할 수 있습니다.`처럼 짧게 알린다.
- 준비 중인 카드에 `바로 처치하기`, `가이드 읽기`, `오프라인 처치 안내 이용 가능` 등을 표시하지 않는다.
- 승인된 항목이 생기면 읽을 수 있는 항목을 먼저, 준비 중 항목을 별도 구역에 표시한다. 이번에 공개 상태가 자동으로 생기는 것은 아니다.
- 공공 일반 경로에서 미승인 원고를 보여주는 우회 버튼을 만들지 않는다.
- 공식 자료 링크는 `공식 자료 열기 · 인터넷 필요` 등으로 기능을 설명한다. 외부 자료가 ERoute에서 검수·승인됐다는 의미를 덧붙이지 않는다.
- 웹사이트가 열리지 않아도 기존 로컬 상태 화면·읽을 수 있는 본문은 유지한다. 오프라인 목록 표시를 오프라인 의료 본문 제공으로 집계하지 않는다.

## 5. 읽기용 상세와 검수용 상세

### 5.1 읽기용 상세

- 제목·적용 대상 → 짧은 안내·119 진입 → 필요한 적용 조건과 본문 → 주의사항·필요한 전환 조건 → 출처·버전 순서로 정리한다.
- 제목과 작은 주제 그림만으로 시작하며, 큰 이미지 때문에 본문 첫 내용을 한참 내려야 보이게 만들지 않는다.
- 실제로 필요한 적용 조건·금기·주의사항은 접힌 출처 영역에 숨기지 않는다.
- `근거: S12`, `미해결 질문`, `검토자 null`, 내부 해시를 매 카드 본문에 노출하지 않는다.
- 출처 상세는 펼쳐보기로 묶어 기관·자료명·원문 버전·확인일·이용 정보와 링크를 제공한다. 실제 검토일과 웹 확인일을 구분한다.
- 단계별 본문은 텍스트·소제목·번호로 표현한다. 전체 화면을 카드뉴스나 WebView로 대체하지 않는다.
- 모든 항목에 같은 임상 절차용 소제목을 강제로 붙이지 않는다. 정보 전달 안내에는 그에 맞는 구성만 사용한다.

### 5.2 개발 검수 상세

- 기존 일반 앱 → 앱 정보 → 개발 검수 경로를 유지한다. 새 Preview 앱을 만들지 않는다.
- 같은 본문 렌더러에 검토용임을 분명히 표시하고, 문장별 근거·질문은 검수 패널에서 볼 수 있게 한다.
- 읽기용 배치를 검수하려면 이 명시적 개발 경로에서 검수 메타데이터를 접을 수 있게 하되, `개발 검토본 · 실제 사용용 아님` 표시는 유지한다.
- 의료 조치를 지시하는 완전한 원고인 것처럼 중립 fixture나 부분 원고를 보여주지 않는다.
- 검수 패널을 접거나 디자인을 승인하는 동작으로 publication manifest가 변경되지 않아야 한다.

## 6. 원고별 공개 조건 정리 — 모든 PENDING을 한 번에 해제하지 않는다

### 6.1 실제 원고·근거 읽기

source-register, decisions, 7개 원고 전체와 실제 참고 자료를 읽는다. 보고서 요약, 원문 링크 제목, 첨부 매트릭스만으로 판정하지 않는다.

현재 자료로 해결할 수 없는 사실을 새로 조사하는 경우 공식 1차 자료를 확인하고, 기존 기록에서 온 내용과 새 조사 결과를 구분한다. PDF 그림·표에 의존하면 실제 페이지 이미지도 확인한다. 기존 부분 원고의 권리 확인을 원문 전체·사진·제3자 이미지에 자동 확장하지 않는다.

### 6.2 항목 유형별로 질문을 점검

- 신고 전달사항·위치 설명은 정보 전달 안내의 정확성·누락·범위·재사용 조건을 중심으로 검토한다.
- 도착 전 준비 중 환자 행동·처치에 영향을 주는 문장은 비임상 안내로 일괄 취급하지 않는다.
- CPR·AED·출혈·화상은 적용 대상·시작 조건·절차·예외·수치·주의·전환 조건의 의료 검토를 유지한다.
- 회원가입 만 14세 기준을 처치 대상 분류에 연결하지 않는다. 원고 간 대상 정의도 자동으로 공유하지 않는다.

예를 들어 신고 안내의 `통화 종료 조건 검토`는 다음을 먼저 확인한다.

1. 기존 원고가 원문에 없는 종료 규칙을 실제로 제안하고 있는가?
2. 임상 처치용 템플릿에 종료 항목이 필수라서 생긴 질문인가?
3. 확인된 원문 범위로 안내를 제한하면서 불필요한 소제목을 없앨 수 있는가?

원문에 없는 규칙을 채워 넣지 않는다. 항목에 적용되지 않는 검토 기준은 이유와 영향을 기록해 `해당 없음`으로 정리하는 안을 제시할 수 있다. 그러나 실제 위험·누락을 단순히 서식 문제로 바꿔 없애거나, 기존 승인 정책을 몰래 완화하지 않는다.

### 6.3 보류 해소 기록

기존 content-matrix를 확장하거나 작은 후속 문서 하나로 다음을 기록한다. 별도의 CMS·승인 서버는 만들지 않는다.

| 항목 | 현재 미해결 질문/문장 | 이유 분류 | 확인한 근거 위치 | 이번에 해결한 내용 | 남은 확인 주체·요청 | 공개 상태 |
|---|---|---|---|---|---|---|

이유 분류는 근거 누락 / 적용 대상 불명 / 권리 불명 / 의료 판단 필요 / 서식상 비적용 / 공개 결정 대기 등 실무적으로 구분한다. 기존 상태 enum과 맞게 최소한으로 관리한다.

- 자료로 해결 가능한 질문은 실제 원고를 수정하고 전후 차이와 근거를 남긴다.
- 확인된 제1유형 텍스트를 이유 없이 별도 허가 대기로 되돌리지 않는다. 이용 범위를 바꾼다면 해당 부분만 다시 확인한다.
- 실제 사람의 의료 검토·별도 허락을 받지 않았으면 받았다고 기록하지 않는다. 검토자·일자를 만들어 넣지 않는다.
- 비임상 안내에 필요한 승인 방식과 임상 안내의 승인 방식이 다르다고 판단하면 근거와 정책 변경안을 명시한다. 자동으로 공개 상태를 올리지 않는다.
- 외부 검토가 남으면 대상 문장·근거·구체적인 질문·검토 범위를 묶은 전달 자료를 만든다. 이메일·문자·문의는 자동 발송하지 않는다.
- 공개 가능한 본문 수를 1건 이상으로 만들기 위해 근거 없는 내용을 추가하거나 필수 검토를 생략하지 않는다.

## 7. 기존 구현을 재사용하는 기술 범위

현 코드에서 먼저 확인할 대상:

- `apps/mobile/lib/features/emergency_guides/{domain,data,presentation}/`
- `apps/mobile/lib/app/router.dart`
- `apps/mobile/assets/guides/ko/`
- `apps/mobile/assets/guide_review/ko/`
- `apps/mobile/test/emergency_guides_test.dart`
- `scripts/verify_emergency_guides.py`

추가할 자산 위치 예시: `apps/mobile/assets/illustrations/guides/`.

- Article ID·라우트·Asset Repository·119 coordinator를 유지하고, 썸네일 asset 경로 등 필요한 메타데이터만 추가한다.
- assets의 실제 경로·크기·해시·제작 방법·원본 출처/이용 범위는 작은 manifest나 문서로 기록한다.
- 제목을 그림에 넣지 않았으므로 Light/Dark에서 글자 대비는 기존 텍스트 테마로 처리한다. 그림별 Dark 파일은 꼭 필요한 경우만 추가한다.
- 이미지를 읽지 못하면 해당 카드만 일반 아이콘으로 대체한다. 제목·상태·탐색은 유지한다. 정상 배포 자산은 누락 검사로 보장한다.
- 장식 이미지의 배포 가능 여부와 처치 본문의 승인 여부는 따로 판단한다. 장식 자산이 공개됐다고 의료 원고를 공개하지 않는다.
- 기존 승인 해시·대상·출처 버전 검사를 우회하지 않는다. 원고나 의미 있는 도해가 바뀌면 기존 승인 기록을 그대로 재사용하지 않는다.
- production APK에는 허용된 공개 메타데이터·썸네일·승인 본문만 포함한다. 개발 원고·검토 질문은 화면 숨김뿐 아니라 실제 번들에서 제외한다.
- 임의 파일 경로, raw HTML, 스크립트, 명령, 콘텐츠 속 tel: 링크를 실행하지 않는다. 외부 출처는 기존 사용자 탭·HTTPS 허용 경계를 유지한다.
- 가이드 열람·이미지 로딩으로 회원·건강정보·위치·병원 provider를 호출하지 않는다.
- Backend·DB·API 계약, 회원 인증, 지도·NMC, 아이콘·런처를 변경하지 않는다.

## 8. 실행 순서와 시각 확인

1. 현재 코드와 원고를 확인하고 이번 수정의 짧은 Plan을 작성한다. 이미 결정한 범위를 같은 질문으로 반복하지 않는다.
2. 기본 한 열 썸네일 카드 한 방향으로 구현한다. 후보 10개나 새 화면 구조를 다시 만들지 않는다.
3. 초기에 두 메뉴의 목록과 대표 상세 한 개의 Flutter 캡처를 비교해 크기·색감·줄바꿈을 확인한다. 이는 의료 공개 승인이 아니다.
4. 같은 스타일로 7개 그림과 일반/검수 화면을 적용하고, 실제 원고의 보류 조건 정리를 병행한다.
5. 기존 검증을 실행하고 최종 일반 APK를 업데이트 설치하여 확인한다.

새 이미지를 이 작업의 디자인 자산으로 실제 제작·적용한다. 텍스트로 ‘이곳에 썸네일 예정’만 적거나 HTML 비교표만 만들고 앱 적용을 완료로 보고하지 않는다.

## 9. 필수 검증·기존 환경 보존

### UI·접근성

- 320/430/720dp, 글자 1/2배, Light/Dark에서 긴 제목·대상·준비 상태·119 버튼이 잘리지 않는다.
- 카드 이미지→제목→대상→상태의 정보가 중복 없이 전달된다. 장식 이미지의 중복 낭독은 제외한다.
- 이미지 누락·디코드 오류에서도 카드 탐색과 다른 문서 접근은 가능하다.
- 실제 TalkBack 한국어 음성·연속 탐색을 수행한 범위만 보고한다. 서비스 활성화나 초점 표시만으로 전체 통과라고 하지 않는다.

### 본문·패키징

- 일반 승인 상세 / 일반 준비 중 상세 / 개발 검수 상세의 노출 차이를 검사한다.
- 직접 상세 route로 이동해도 미승인 본문은 일반 경로에 나타나지 않는다.
- 숨김 해제·검수 패널 토글·썸네일 갱신으로 공개 manifest가 변하지 않는다.
- dev와 production APK ZIP 내부의 이미지·본문·검수 정보 포함 목록을 실제 검사한다.
- 승인된 본문이 0이면 임상 본문 오프라인 제공 검수는 `해당 공개 대상 없음`으로 보고한다. 가짜 승인 임상 원고를 production에 넣지 않는다.

### 오프라인·독립성·119

- 비회원·세션 복원 지연·동의 없음·GPS 거부에서도 목록과 허용 상세가 열린다.
- 기존 사용자 데이터를 지우지 않는 격리 대상에서 캐시 없는 오프라인 첫 실행을 확인한다. 목록 썸네일도 처음부터 보인다.
- 외부 출처 링크 실패와 내부 로컬 열람은 별개로 처리한다.
- 실제 PASS·SMS·ACTION_DIAL·tel:119·전화 launcher를 실행하지 않는다. 기존 Mock coordinator로 취소·확인·중복·실패만 검사한다.
- 가이드 전용 NMC·식약처·HIRA 호출은 0회로 검증한다. 웹 근거 조사·수동 원문 링크 확인과 앱 가이드 트래픽을 구분한다.

### 빌드·설치

- 기존 local 인증, Backend 주소, 지도 Client ID, 서명·ID를 확인한 뒤 기존 `scripts/run_mobile.py` 설정 주입 경로를 사용한다.
- 현재 값이 누락돼 있으면 과거 보고서를 참고해 대조하되, 비밀이나 현재 설정을 추측해서 채우지 않는다. `auth=disabled` 기본값으로 사용자 앱을 덮어쓰지 않는다.
- 실제 설치본 ID·서명 확인 후 업데이트 설치한다. 앱 삭제·앱/런처 데이터 초기화·DB 초기화로 우회하지 않는다.
- 회원 세션 복원 과정의 정상 토큰 갱신을 바이트 불일치라는 이유로 초기화로 오판하지 않는다.
- Backend·DB·에뮬레이터·사용자 작업을 임의 종료하지 않는다. 변경한 글씨·테마·네트워크·접근성·Android 사용자 설정은 복구한다.
- 기존 디자인·아이콘·전화 정책·회원 화면 보호를 그대로 유지한다.

## 10. 완료 보고와 다음 작업

문서 경로 제안:

- `docs/ui/guide-thumbnails-v1/`: 자산 설명·원본/파생 기록·비교 화면
- `docs/content/emergency-guides/`: 갱신된 원고·매트릭스·검토 요청
- `docs/qa/guide-reader-v1_1-<실제 검수일>/`: 명령·테스트·실제 캡처·설치 식별정보

보고 항목:

1. 실제 적용된 썸네일 수, 메뉴별 변화, 일반/검수 상세의 차이.
2. 원고별 해결된 질문, 남은 질문과 담당 분야, 공개 가능한 본문 수.
3. 공개 승인·전문가 검토·권리 확인·웹 확인·UI 승인의 구분.
4. 두 목록, 준비 중 상세, 개발 읽기 레이아웃, 출처 펼침, 이미지 오류 fallback, 오프라인·큰 글씨·Dark 캡처.
5. 최종 일반 APK ID·버전·빌드 시각·SHA-256·서명·설치본 일치.
6. Flutter analyze와 실제 테스트 결과, production 패키징 검사, 외부 호출·launcher 관측 범위.
7. iOS·실물 기기·TalkBack·의료 검토의 미검증 항목과 남은 실행 환경.

완료 표현 예시:

`썸네일 7개와 읽기용 레이아웃 적용 완료 / 개발 원고 7건 중 질문 N건 해결 / 공개 본문 X건 / 외부 검토 대기 Y건`.

X가 0이면 그대로 보고한다. 전체 가이드 서비스 완료라고 표시하지 않는다. 외부 검토가 남은 이유와 다음 확인 주체를 명확히 인계하고 사용자 검수를 기다린다.

기저질환 관련 진료과 표시 v1 → 식약처 실제 검색 → HIRA 근거 보강은 후속 순서로 유지한다. 이번 작업에서 자동으로 확장하지 않는다.
